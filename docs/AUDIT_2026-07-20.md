# ATAS 1.2.0 third-pass release audit — 2026-07-20

## Scope

This audit reviewed the ATAS 1.1.0 baseline and the complete 1.2.0 change set as a safety-oriented software release. It covered deterministic timing, clock integrity, concurrency, retry behaviour, PostgreSQL constraints, auditability, realtime recovery, authentication boundaries, deployment failure modes and submission readiness.

The review did not include an external penetration test, independent safety certification, a real stadium integration, annotated-match validation, referee usability testing or an authorised competitive trial.

## Material findings resolved

### 1. Match ruleset could diverge from the ruleset loaded at process start

**Risk:** a historical or long-running match could be recalculated with the wrong policy after a deployment.

**Resolution:** the engine now loads the immutable ruleset bound to `match.ruleset_id`, and startup verifies the pinned bundled ruleset digest.

### 2. Live calculation accepted caller-supplied time

**Risk:** a client could move the operational clock.

**Resolution:** the operational endpoint uses only authenticated append-only clock samples. The explicit `nowUs` endpoint is labelled and authorised as diagnostic/replay only.

### 3. Asynchronous samples produced false drift

**Risk:** samples received at different times appeared inconsistent even when clocks were correct.

**Resolution:** all samples are projected to one database-observed instant before residual comparison. Fresh operational drift is separated from stale diagnostic drift.

### 4. Redundant clocks could freeze together

**Risk:** two or more devices could stop advancing while remaining mutually consistent, causing a common-mode failure to look healthy.

**Resolution:** the projected primary clock is independently compared with PostgreSQL time elapsed since the official period start. Exceeding `CLOCK_MAX_WALL_DRIFT_US` makes the recommendation `WITHHELD` even when source quorum is met.

### 5. PostgreSQL transaction timestamps could predate actual execution

**Risk:** `now()` is fixed at transaction start. A command waiting behind a per-match lock could record an inaccurate period start/end or evidence timestamp, corrupting wall-clock correlation.

**Resolution:** operational updates and defaults use `clock_timestamp()`. Migration `005_wall_clock_timestamps.sql` applies this to match/evidence/audit/outbox timestamps.

### 6. Displayed board value could change after announcement

**Risk:** when measured loss exceeded the announced minimum, floor/ceiling fields could imply a different board value after the fourth official had displayed it.

**Resolution:** after announcement, both board fields remain fixed to the official integer. The exact target still uses the larger of measured loss and announced minimum, preserving the rule that the minimum may be increased but not reduced.

### 7. WebSocket delivery was not durable

**Risk:** a lost notification could leave clients silently stale.

**Resolution:** PostgreSQL outbox rows are the durable source; WebSockets are wake-up hints. Clients recover through an ordered cursor, and per-match retention watermarks explicitly report an expired cursor.

### 8. Realtime listener readiness could miss a half-open connection

**Risk:** a TCP connection could remain present while `LISTEN` delivery had stopped.

**Resolution:** the dedicated listener performs active SQL heartbeats. Readiness fails when the last successful heartbeat becomes stale, forcing the orchestrator to replace the instance.

### 9. Startup and shutdown could leak resources or hang

**Risk:** a listener/worker bootstrap failure or blocked close could leave sockets, timers or database connections alive and interfere with rollout.

**Resolution:** failed startup rolls back allocated resources. `SHUTDOWN_TIMEOUT_MS` bounds graceful termination and forces a non-zero exit when cleanup cannot complete.

### 10. Outbox retention could make cursors ambiguous

**Risk:** clients could not distinguish “no new change” from “your cursor predates retained history”. Cleanup could also grow into a latency event.

**Resolution:** cleanup is published-only, bounded, single-leader and records a per-match high-water mark. Cursor state and signed checkpoints use the maximum of retained and current IDs.

### 11. Hash canonicalisation depended on locale

**Risk:** `localeCompare()` can order object keys differently across ICU/locale builds, causing otherwise identical audit payloads to hash differently.

**Resolution:** all new records use fixed ordinal key ordering (`ATAS-ORDINAL-1`). Verification retains explicit compatibility for legacy 1.1 records.

### 12. Internal hash chains could be truncated at the tail

**Risk:** a database/HMAC administrator could remove the newest valid rows and leave the remaining chain internally consistent.

**Resolution:** ATAS exports Ed25519-signed external checkpoints containing chain counts/heads, ruleset digest, migration set and durable cursor. The exporter verifies exact schema compatibility and all chains before signing.

### 13. Cross-match JWT authority was too broad

**Risk:** a valid operator or official token could act on another match.

**Resolution:** production requires explicit match UUID scopes. Only controlled administration can use wildcard scope. Sensor identities remain ingest-only and cannot read or confirm evidence.

### 14. Retry paths could duplicate logical effects

**Risk:** network retries could create duplicate matches, evidence, audit records or notifications.

**Resolution:** client UUIDs, source sequences, canonical replay comparison and state-idempotent commands make exact retries harmless and reject conflicting reuse.

### 15. Arbitrary evidence JSON could exhaust canonicalisation

**Risk:** deeply nested or highly fragmented JSON could consume CPU/memory or overflow recursive processing.

**Resolution:** metadata and evidence are validated iteratively with explicit depth, node, key, array and string bounds before hashing or persistence.

### 16. Older software could run against a future schema

**Risk:** a partial rollback could start old code on a database changed by a newer release.

**Resolution:** startup and checkpoint export require the exact supported migration filenames and checksums and reject unexpected future migrations.

## Verification performed

- Node.js 24.18.0 / npm 10.9.2 exact target runtime.
- Formatting, type-aware lint, strict TypeScript and production compilation passed.
- 55 deterministic/unit regression tests across 11 files passed.
- Coverage completed: 75.58% statements and 76.87% lines overall; the pure timing engine reached 88.88% statements and 88.78% lines.
- Production dependency audit reported zero known vulnerabilities.
- Production dependency tree resolved; only documented optional native WebSocket accelerators were absent.
- Five PostgreSQL migrations parsed successfully: 56 SQL statements total.
- Seven JSON files and 18 YAML/CFF documents parsed successfully.
- Shell entrypoint syntax and Git whitespace checks passed.
- Package dry run completed without secrets, build output or dependency directories.

## Residual risks and mandatory next work

1. Run the configured PostgreSQL 17 integration and Docker image jobs in GitHub Actions after publication; this workspace has no PostgreSQL or Docker runtime.
2. Commission independent code, penetration, privacy and safety reviews.
3. Add property-based/fuzz testing for interval calculation, canonicalisation and API schemas.
4. Execute concurrency, load, soak, chaos, restore and database failover exercises.
5. Replace locally managed shared JWT signing with a tournament identity service or asymmetric offline-capable key architecture before a high-assurance deployment.
6. Protect HMAC/checkpoint keys with HSM/KMS procedures and independently publish trusted public-key fingerprints.
7. Validate clock adapters and the period-wall tolerance through metrology testing on actual stadium hardware.
8. Build and adjudicate an annotated historical match corpus without tuning against the final evaluation set.
9. Complete referee/operator human-factors testing, training and manual fallback drills.
10. Obtain written organiser, governing-body and, where required, IFAB approval before any competitive influence.

## Audit conclusion

No unresolved critical defect was identified within the static, deterministic and unit-tested scope of this review. ATAS 1.2.0 is a materially stronger baseline for replay, laboratory integration and non-influential shadow evaluation. The residual work above prevents any claim of FIFA/IFAB certification, autonomous authority or readiness to influence a competitive match.
