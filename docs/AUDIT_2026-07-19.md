# ATAS 1.1.0 release audit — 2026-07-19

## Executive conclusion

ATAS 1.0.0 was a credible engineering baseline, but it contained two material gaps that prevented a serious operational pilot:

1. calculations used the ruleset loaded at process startup instead of always loading the immutable ruleset bound to the match;
2. the operational estimate accepted a client-supplied match clock and had no authenticated, replay-protected authoritative clock feed.

ATAS 1.1.0 corrects both issues and adds database-enforced immutability, sensor replay protection, redundant-clock supervision, strict PostgreSQL `bigint` decoding, capability-based authorisation, safer deployment defaults, and a hardened browser console.

This audit does **not** claim FIFA/IFAB certification, safety certification, or permission to influence an official match. Independent verification, a supporting football body, controlled shadow trials, and governing-body approval remain mandatory.

## Findings and remediation

### Critical / high

#### Match-bound ruleset was not used by the engine

**Risk:** historical or competition-specific matches could be recalculated using a different ruleset loaded at service startup.

**Fix:** every calculation now resolves `matches.ruleset_id` and loads that immutable ruleset from PostgreSQL. Regression tests verify the binding.

#### Client-supplied clock was usable as the main operational clock

**Risk:** a browser/operator could move `nowUs`, affecting active intervals and the target end.

**Fix:** the operational endpoint is now `/estimate/live` and is driven only by authenticated clock samples. The explicit `nowUs` endpoint remains restricted to operator-level diagnostic/replay use and is labelled accordingly in OpenAPI.

#### Clock feed lacked replay protection and integrity history

**Risk:** duplicate, reordered, or altered clock messages could corrupt the live timeline.

**Fix:** clock messages require a source identity from the JWT, a monotonic source sequence, and non-decreasing elapsed time. Identical retries are idempotent; sequence reuse with different content is rejected. Samples form an HMAC-SHA-256 chain.

#### Database append-only guarantees were application conventions

**Risk:** direct SQL could update or delete event, stoppage, clock, audit, or ruleset evidence.

**Fix:** PostgreSQL triggers reject `UPDATE` and `DELETE` on all append-only evidence tables and immutable rulesets.

#### PostgreSQL `bigint` values could lose precision silently

**Risk:** match-relative microseconds and sequence columns use PostgreSQL `bigint`. JavaScript cannot exactly represent every signed 64-bit value, and permissive conversion could silently round evidence identifiers or timestamps.

**Fix:** ATAS installs a strict `int8` decoder that accepts only syntactically valid values inside JavaScript's safe-integer range and fails closed otherwise. Unit tests cover exact, malformed, and out-of-range inputs.

### Medium

#### Single-clock visibility

**Risk:** a fresh but incorrect primary clock could remain undetected.

**Fix:** the engine compares all authorised fresh clock sources. It retains one explicit primary source for deterministic calculation, but requires a configurable fresh-source quorum and checks maximum drift. Missing quorum or excessive drift produces `REVIEW_REQUIRED`; a missing/stale primary produces `WITHHELD`.

#### Sensor duplicates could create repeated events

**Risk:** retries from networks or adapters could double-count a logical interruption.

**Fix:** sensor submissions must include a stable UUID `eventId`. Identical retries return the existing logical event; conflicting reuse is rejected.

#### Linear role hierarchy over-granted sensor access

**Risk:** treating `sensor` as a level above `viewer` allowed machine credentials to inherit read access and allowed unrelated higher roles to enter clock-ingestion paths.

**Fix:** read, event-ingest, clock-ingest, operator, and official actions now use explicit role capabilities. Sensor credentials are ingest-only; clock ingestion is limited to authorised sensor identities and controlled admin maintenance.

#### Boundary handling depended on duplicate stoppage entry

**Risk:** a confirmed delay event crossing 45:00/90:00 could be classified incorrectly if an operator forgot to create a separate `play_stoppage` record.

**Fix:** the engine now uses confirmed/corrected event raw intervals as boundary-stoppage evidence in addition to explicit stoppage records. A regression test covers the missing-duplicate case.

#### Event timestamps could be ahead of live play

**Risk:** a source could pre-create future intervals and distort later results.

**Fix:** when an authoritative clock exists, event/stoppage times beyond the configured future tolerance are rejected.

#### Browser console retained JWT in local storage

**Risk:** a token persisted across sessions and was more exposed to local compromise.

**Fix:** JWTs are memory-only. Only the non-secret match ID is stored in `sessionStorage`. Event rows are built with DOM `textContent`, eliminating dynamic `innerHTML`. WebSocket reconnect includes exponential backoff and REST resynchronisation.

#### Default container exposed the application directly

**Risk:** `/metrics` and the API were reachable without the intended edge policy.

**Fix:** Docker Compose now places the application only on an internal network and exposes Caddy. Caddy blocks `/metrics`, adds security headers, and proxies the API. Prometheus remains on the internal network.

#### Release image tags did not match deployment manifests

**Risk:** the tag workflow produced `v1.1.0` while Kubernetes referenced `1.1.0`; the mixed-case GitHub owner could also produce a non-portable GHCR path.

**Fix:** release metadata now publishes `v1.1.0`, `1.1.0`, the major/minor tag, and `latest` under the canonical lowercase image name `ghcr.io/liliumfra/atas`.

## Known residual risks

- HMAC chains are not non-repudiation if an attacker obtains both the database and HMAC secret. A federation deployment should anchor chain heads in an HSM-backed external transparency service.
- PostgreSQL `LISTEN/NOTIFY` is transient; WebSocket messages are hints and clients must resynchronise through REST.
- The included JWT utility is not a complete federation identity lifecycle. Production should use managed OIDC/mTLS and hardware-backed device identities.
- Automated event detection models are outside this repository and require their own performance, bias, failure-mode, and cybersecurity validation.
- The reference grace thresholds are engineering parameters, not official fixed IFAB values.
- Human factors, accessibility, stadium integration, performance under tournament-scale load, and disaster-recovery drills still require independent testing.

## Release recommendation

Suitable for:

- deterministic replay;
- laboratory evaluation;
- historical dataset validation;
- shadow operation in non-match-control mode;
- preparation of a FIFA Innovation Programme application.

Not yet suitable for:

- autonomous match termination;
- direct control of the fourth official's board;
- use in a competitive match without explicit governing-body and, where required, IFAB written approval.
